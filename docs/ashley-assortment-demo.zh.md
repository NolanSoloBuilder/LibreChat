# Ashley 企业选品 Agent 演示方案

2026-09-20 修订；待评审，尚未实施。本文是一项任务内的选品 workflow 设计，不代表已经核实 Ashley 内部 SOP、真实经营数据或接口能力。

## 1. 演示要回答的业务问题

让区域商品经理为下一季门店上样形成可讨论、可修改、可保存的商品组合，而不只是生成一份趋势报告。成功产物包括每家店选什么、为什么、预算与交期是否满足、哪些数据待核实，以及用户修改条件后发生了什么变化。

演示对象暂定为区域商品负责人和门店负责人。暂不覆盖总部新品研发、跨境新品引入、正式采购或审批；这些场景的输入与责任不同，不混在首个演示中。

经营服务使用模拟数据；当前版本另收录 29 个 Ashley 官网商品公开快照（名称、图片、美元标价；其中 5 款含官网尺寸），来源与采集时间可追溯。人民币报价、库存、交期和市场信号仍是合成数据。开始页或首条回复展示“企业演示数据”，每个结果保留数据来源标识。企业服务是 mock，HTTP/MCP 请求、参数过滤、计算、状态保存和模型分析真实执行。

## 2. 业务场景与可核算的演示口径

建议用户开场：

> 帮华东三家店准备下一季的小户型沙发上样方案，每店两款，总预算 2.4 万，45 天内到店，尽量年轻一点。

暂定的模拟企业背景：

| 项目 | 演示口径 |
| --- | --- |
| 决策范围 | 已有商品池中的沙发上样，不预测销量，不生成采购订单 |
| 门店 A | 小户型年轻家庭，兼顾耐用与可清洁性 |
| 门店 B | 年轻租住客群，价格敏感、展区有限 |
| 门店 C | 改善型客群，关注舒适、材质和风格一致性 |
| 组合要求 | 每店 2 款，每款上样 1 件，共 6 件；全区域最多 3 个不同 SKU，便于集中展示与培训 |
| 预算定义 | 6 件样品的采购与到店物流预算合计不超过 24,000 元，不是零售价总额 |
| 商品要求 | 目标单件零售价 4,000–8,000 元、宽度不超过 2.2 米、45 天内可到指定门店 |
| 模拟政策 | 单 SKU 预计商品毛利率至少 40%；不满足或成本缺失的商品不得进入“已校验可执行”方案 |
| 货币与毛利 | 人民币；演示价格统一使用同一未税口径，毛利率=(计划零售价−采购成本−分摊到店物流)/计划零售价；不等于门店净利润 |
| 日期 | 使用固定且显式展示的演示基准日期，交期相对该日期计算；不伪装成当天真实库存 |

以上数字均为设计输入，不是已生成的数据集。造数后必须由确定性校验脚本证明：45 天至少存在两套可行组合；30 天仍有替代组合；更严条件确实可能无解。不得先写死推荐结论再伪造工具结果。

Agent 先读取模拟门店与政策，然后只追问真正影响判断的缺项，例如“2.4 万是否包含物流”“上样商品是否需三店一致”。已由企业配置提供的尺寸和毛利政策不重复问用户。柔性偏好“年轻一点”需转化为可解释属性，不能直接当作量化销量预测。

## 3. 单任务流程与可见结果

| 阶段 | 实际业务动作 | Agent 的职责 | 服务端必须保证 | 用户看到什么 |
| --- | --- | --- | --- | --- |
| 需求确认 | 明确门店、件数、预算、时限和商品约束 | 读取背景、识别缺项、集中追问，区分硬约束与偏好 | 保存任务和需求版本，不把未知值填成零 | 简短需求卡；确认后开始 |
| 信息准备 | 查商品池、市场信号和门店属性 | 在参数独立时并行查；将“年轻”转成风格、尺寸、材质等证据 | 检索可重复、记录来源和日期；陈旧信号明确标记 | 简短进度及依据，例如需求与商品属性对应关系 |
| 初筛 | 找出符合尺寸与价格的候选 | 聚合跨来源证据，指出信息冲突和缺项 | 固定过滤规则、SKU 去重、不得填造缺失成本 | 候选数及淘汰原因，数量来自当次工具结果 |
| 经营校验 | 查区域库存、在途、交期、成本，计算组合 | 提出可选组合，解释各店分配与取舍 | 校验共享库存的总需求、预算、毛利、SKU 数与门店件数 | 按店分配表、校验结果、不可选/待核实商品 |
| 方案比较 | 比较两套都可行的上样方案 | 给出主推与替代方案，说明侧重和代价 | 仅对通过硬约束的方案比较；无销量数据不得写收益预测 | A/B 方案与推荐理由，不只是一串商品 |
| 条件变更 | 用户将 45 天改为 30 天或调整门店偏好 | 判断受影响数据，重查供应并重算；未变的证据可复用 | 需求版本递增，旧校验失效，禁止保存旧版本方案 | 保留/替换 SKU、原因、成本与交期变化 |
| 确认并保存 | 用户确认具体方案与版本 | 发起带审批确认的草稿保存，返回真实结果 | 服务端再次校验、幂等保存；失败不得声称已保存 | 草稿编号、版本、分店清单、待办与来源 |
| 继续讨论 | 打开已有草稿或追问为何淘汰某款 | 按保存状态和证据回答，必要时创建新修订 | 草稿可回读，不依赖聊天摘要恢复业务状态 | 可读取的草稿与修订记录 |

这是一段可交互的任务流程：用户插话不会新建无关任务。只在明确需求、改变硬约束、保存草稿等关键点让用户参与，不逐工具弹出确认。

缺失成本的候选可展示为“待核实”，但不能混进声称已满足毛利门槛的最终组合。若无可行方案，工具返回冲突约束，Agent 给出需要用户选择的放宽方向；不能自行提高预算或降低政策门槛。

## 4. 智能体设计

### 首版一个主 Agent：选品顾问

Ashley 是产品品牌；“选品顾问”是业务 Agent；OpenAI/GPT 等仍是供应商与模型身份。配置实际 Agent，而不是再把普通模型显示预设命名成业务助手。

主 Agent 负责四类判断：需求澄清、证据整理、组合解释、条件变更后的重规划。市场、商品、供应分析是它的阶段职责，首版不拆成三个相互聊天的 Agent。这样用户看到一位负责人，也便于追踪一个任务和一份方案。

Agent 指令需覆盖：

- 开始时说明数据为演示数据，读取业务上下文后再追问。
- 使用服务端返回的 SKU、成本、库存、交期与计算值；推断和事实分开。
- 只把通过 evaluate_selection 的当前需求版本方案标为可执行候选。
- 解释“为什么选、为什么不选、替代的代价”，不展示内部思维链。
- 条件变更时只更新受影响步骤，但任何组合变更必须重新校验。
- 保存前展示当前版本摘要并通过平台工具确认；不得用模型自填 confirmed=true 代替用户确认。
- 不具备真实采购、付款或企业审批能力，不声称已经发单。

模型先采用已验证对话可用的 GPT-5.6 Luna。实施时需要新增工具选择、参数准确性、多轮修订和失败处理验收；若表现不足，再用 Terra 做相同用例对照，不凭型号推定业务效果。

## 5. Workflow 如何落地

复用 LibreChat 的 Agent/工具执行循环，增加一个独立 selection-demo MCP 服务。无需首版搭建通用 DAG 编辑器或新的 Agent 引擎。

```text
Ashley / LibreChat
  选品顾问 Agent：理解、规划、调用工具、解释
                 ↓ MCP
selection-demo 服务
  需求版本 / 模拟数据查询 / 规则计算 / 草稿保存
                 ↓
固定演示数据集 + SQLite 持久化（独立 Docker volume）
```

模型决定查询策略与表达方式；业务服务负责不可跳过的规则。内部用小型任务状态和版本记录即可，不将自然语言提示词当成流程控制。

建议状态：`collecting → evaluating → proposed → saved`。用户确认绑定具体 proposal_version；它不是模型可随意赋值的状态。需求或组合变更会使原校验和原确认失效；需要重算和重新确认。任务状态存于业务服务，LibreChat 对话只保存 task_id 引用。

保存通过 LibreChat 工具审批交互取得用户确认后继续调用；实施前验证当前运行镜像与 MCP 工具的审批接线。如果无法可靠绑定确认到指定版本，首版应补显式确认入口/令牌绑定，不能退化为模型自行声明“用户已确认”。这不是企业多级审批。

业务时间跨度仅覆盖演示任务；支持刷新后读取草稿。跨进程自动续跑、跨天任务调度和采购事务补偿不在首版完成承诺中。

## 6. 企业工具与数据合同

只部署一个 MCP 服务，内部模拟多个企业系统。第三方 HTTP API 如需展示，可作为 MCP 内部的 adapter；首版优先本地固定数据，避免外部网络和配额影响复演。

| 工具 | 模拟来源 | 输入与输出重点 |
| --- | --- | --- |
| get_selection_context | 门店主数据、政策中心 | 门店 ID → 门店画像、展位约束、预算口径、政策版本 |
| upsert_selection_brief | 选品任务系统 | task_id、期望版本、约束 → task_id、brief_revision、缺项与冲突；变更使旧校验失效 |
| search_market_signals | 市场研究/社媒数据服务 | 区域、品类、客群、时间 → signal_id、观察值、样本口径、日期与模拟来源 |
| search_catalog | PIM 商品中心 | 属性过滤、区域、分页 → SKU、图片引用、属性、报价与成本缺项 |
| get_supply_availability | ERP/WMS/供应链 | SKU、门店、数量、目标日期 → 区域可用量、在途、最早到店时间、查询快照 |
| evaluate_selection | 经营规则服务 | task_id、brief_revision、按店 SKU 与数量 → validation_id、通过/失败、预算、毛利、库存分配、失败原因 |
| save_selection_draft | 方案管理 | task_id、需求/方案版本、validation_id、幂等键 → 真实 draft_id、版本、状态；再次校验 |
| get_selection_draft | 方案管理 | draft_id → 持久化内容、证据引用、修订记录 |

共同返回：`data_mode=mock`、`dataset_version`、`as_of`、`record_id/source_id`、必要的币种和单位。查询结果有数据新鲜度与完整性标记。工具错误用稳定错误码，允许解释“库存接口暂不可用”或“需求版本已变化”，不输出凭据和内部堆栈。

查询失败可做有限重试；写入结果未知时先按幂等键读取，不直接重复创建草稿。推荐依据使用真实返回记录；来源链接只能指向存在的演示记录页或明确模拟来源，不伪造外部报道 URL。

## 7. 数据准备与有业务意义的转折

建议准备约 30 个 SKU、3 家门店、约 40 条市场观察及关联的库存/成本/交期记录。图片可使用有权使用的素材；生成图必须标记为示意，不能据图推断实物尺寸和质量。

数据集应有以下可复现关系，具体 SKU 组合由工具计算后确定：

1. **热门但不适配**：市场关注较高的款式宽度超标，或到货晚于 45 天，明确淘汰。
2. **相似但经营结果不同**：两款外观近似，成本、物流、交期不同；AI 解释为何选其中一款。
3. **缺失信息**：一款成本未知，不能计算确定毛利。
4. **门店差异**：同一款对 A 店适合，对 B 店可能占地或价格不合适。
5. **共享库存约束**：一个 SKU 区域仅剩 1 件，不能同时给三店各分 1 件。
6. **交期变更**：30 天需求使原方案部分 SKU 失效，但有合规替代；产生非零的组合差异。
7. **不可行分支**：用户同时要求极短交期和更低预算，确实无解，系统明确提出需放宽的约束。
8. **服务故障**：供应服务暂时失败，界面保留已完成信息，未查到的数据不填作“有货”。

正常演示用固定种子；异常用显式演示场景开关。所有案例可重置，不需要清空用户正常聊天数据。

## 8. 10–12 分钟演示脚本

| 时间 | 用户/讲解动作 | 应展示的能力 |
| --- | --- | --- |
| 0–1 分钟 | 说明企业数据为模拟，进入选品顾问，输入业务需求 | Ashley 品牌与业务任务入口 |
| 1–2 分钟 | 回答一轮必要问题，确认采购含物流预算 | AI 理解口语并形成可执行需求 |
| 2–5 分钟 | 观察工具调用、候选筛选和两套方案 | 多源整合、真正计算、可解释取舍 |
| 5–6 分钟 | 问“为什么没选那款热门的？” | 基于 SKU 和硬约束追溯证据 |
| 6–9 分钟 | 改为“30 天内到店，B 店更看重易清洁” | 按影响范围重查、重新分配、展示差异 |
| 9–10 分钟 | 选择一套并确认保存 | 从建议落到可持久化业务草稿 |
| 10–12 分钟 | 重新读取草稿；可选提出一个不可行条件 | 任务可续接、不为迎合用户伪造可行解 |

时间是目标，不是现有性能实测。应有清晰进行中状态，先返回简短进度，不让用户盯着长时间空白。主线最多三次主动确认，异常演示作为备选，不把所有分支塞进一场演示。

## 9. 交互与产物

沿用 LibreChat 对话、工具卡、Markdown 表格。首版不另做大屏或拖拽 workflow 画布。

- 需求卡：硬约束、偏好、未确认项。
- 候选表：SKU/缩略图引用、适用门店、零售价、成本、交期、证据与校验结果。
- 方案表：每店 2 款、数量、预计上样预算、剩余预算、毛利门槛检查、缺项。
- 修订差异：换出/换入、触发原因、预算变化、交期变化。
- 草稿回执：draft_id、版本、状态、来源快照与待办。

图片卡、图表和 Artifact 若原生能力可用再增强；基础表格必须独立完成任务。所有看似精确的分数都需规则可解释，首版优先事实对照，不创造未经校准的“畅销概率”。

## 10. 开发边界、顺序与验收

已有底座：账号、模型调用、Agent 配置入口、MCP/Actions 接入、工具执行展示、对话存储。已实测模型对话与标题；当前本地没有已配置的业务 Agent/MCP，Codewiz 多步工具调用与审批恢复尚未验收。

需要配置：选品顾问的指令、模型、可用工具、写工具审批。

需要开发：mock MCP、数据集、确定性规则与分配校验、任务/草稿持久化、幂等、错误语义、验证脚本。不是只写一段系统提示词即可完成。

交付阶段：

1. **合同与数据**：明确场景口径，种子数据与计算测试证明 45 天、30 天、无解三类场景。
2. **最小工具链**：读取任务 → 查商品/供应 → evaluate；验证当前 LibreChat + Codewiz 的真实工具调用、多轮与可见结果。
3. **完整流程**：差异修订、版本失效、用户确认、草稿保存与回读。
4. **现场验收**：用从未预写的偏好修改再演练一次，检查实际工具参数与结果；补异常和重启后草稿回读。

验收必须满足：

- 展示数量、价格、库存、推荐与原因均能追溯到当次工具返回；调用轨迹和最终表格一致。
- 六件上样数量、区域共享库存、预算、毛利、交期与不同 SKU 数均由服务端计算，不接受模型自报。
- 需求修改后不允许旧 validation_id 保存；无解时不偷偷放宽硬约束。
- 保存经用户确认，重复提交不重复创建草稿，刷新/服务重启后可回读。
- 模拟数据全程可辨；产品 Ashley、业务 Agent 选品顾问、供应商/模型三层身份分开。
- 基础版本以真实业务端到端演示为完成态；Gemini/Claude/所有已列模型工具能力、真实企业接入、跨天运行不借用对话 smoke 结果背书。

评审重点：演示对象是否是区域商品经理；上样而非采购是否合适；模拟门店/预算/件数口径是否贴近目标客户。方案已获确认并实施，运行方式与验收记录见 [实现说明](../services/selection-demo/README.md)。
